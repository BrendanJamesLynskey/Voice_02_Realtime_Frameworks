01

Why a Real-Time Framework

A voice bot is not a request–response service. It is a stateful, bidirectional audio stream that must handle overlapping microphone input, partial ASR results, LLM token streams, TTS audio chunks, user interruptions, and telephony-level protocol requirements — all simultaneously, all with sub-second deadlines.

Wiring this by hand with asyncio queues produces spaghetti that breaks when you swap a TTS provider or add a second language. A real-time framework gives you:

What a framework provides

  • Transport abstraction (WebRTC, WebSocket, Twilio, PSTN)
  • Pipeline / processor model with typed frame passing
  • Pluggable ASR / LLM / TTS service adapters
  • VAD, turn-taking, and interruption handling
  • Audio mixing, resampling, and jitter-buffer management
  • Observability hooks (metrics, traces, conversation logging)

What you still own

  • Business logic — system prompt, tool definitions, guardrails
  • State machine — conversation context, session data
  • Provider selection — which ASR / LLM / TTS to use
  • Deployment — container, scaling, PSTN number provisioning
  • Evaluation — call recording, transcript analysis, WER/MOS audit
The two viable open-source options

Pipecat (Daily, v0.0.49 as of Q1 2026) is a Python pipeline framework that works with any transport and any service. LiveKit Agents (LiveKit, v0.x) is tightly coupled to LiveKit’s WebRTC infrastructure but ships built-in telephony, SIP trunking, and a managed cloud. Both are MIT-licensed.

Pipecat Architecture — Pipeline, Processors, Services

Pipecat models a voice bot as a directed graph of processors connected by asyncio queues, running inside a pipeline. Each processor consumes typed frames from its input queue and emits frames to its output queue. The framework handles scheduling; processors are single-task coroutines.

Frame types (pipecat.frames.frames)

Frame classDirectionPayload
AudioRawFrameIn & outraw PCM bytes, sample_rate, num_channels
TranscriptionFrameASR → LLMtext, user_id, timestamp, is_final bool
LLMMessagesFramecontrolOpenAI-style messages list for context injection
TextFrameLLM → TTSraw text string (one token or one sentence)
TTSStartedFrame / TTSStoppedFrameTTS → outputmarker for playout lifecycle; used by VAD to suppress echo
UserStartedSpeakingFrameVAD → pipelinetriggers interruption logic in LLM processor
FunctionCallResultFrametool layerresult dict to inject back into LLM context

Minimal bot pipeline

python — pipecat 0.0.49 minimal voice bot
from pipecat.pipeline.pipeline import Pipeline
from pipecat.pipeline.runner import PipelineRunner
from pipecat.pipeline.task import PipelineTask
from pipecat.transports.services.daily import DailyTransport, DailyParams
from pipecat.services.deepgram import DeepgramSTTService
from pipecat.services.openai import OpenAILLMService
from pipecat.services.cartesia import CartesiaTTSService
from pipecat.processors.aggregators.openai_llm_context import OpenAILLMContext
from pipecat.vad.silero import SileroVADAnalyzer

transport = DailyTransport(room_url, token,
    "MyBot", DailyParams(audio_in_enabled=True,
                               vad_analyzer=SileroVADAnalyzer()))

stt = DeepgramSTTService(api_key=DG_KEY, model="nova-3")
llm = OpenAILLMService(api_key=OAI_KEY, model="gpt-4o-mini")
tts = CartesiaTTSService(api_key=CA_KEY, voice_id=VOICE_ID)
ctx = OpenAILLMContext([{"role": "system", "content": "You are a helpful assistant."}])

pipeline = Pipeline([
    transport.input(),   # AudioRawFrame from WebRTC
    stt,                   # → TranscriptionFrame
    ctx.create_processor(), # builds messages list
    llm,                   # → TextFrame (streaming tokens)
    tts,                   # → AudioRawFrame
    transport.output(),  # sends PCM to WebRTC peer
])

runner = PipelineRunner()
task   = PipelineTask(pipeline)
await runner.run(task)
Processor isolation

Each processor runs as an independent asyncio.Task. Swapping Deepgram for AssemblyAI means replacing one constructor call; the rest of the pipeline is unaffected. Pipecat’s design goal is that every service adapter is a 10-line subclass of AsyncProcessor — a constraint that has held well across the current 60+ built-in adapters.

LiveKit Agents — Built on WebRTC

LiveKit Agents is an agent SDK that runs inside a LiveKit room. A LiveKit room is a WebRTC conference with a server-side signalling infrastructure (SFU). Your agent process joins as a participant, subscribes to audio tracks, and publishes audio back. The transport layer is DTLS-SRTP, giving you NAT traversal, jitter buffers, and packet-loss concealment for free.

Agent lifecycle

WorkerOptions: entrypoint=my_entrypoint, auto_subscribe=AutoSubscribe.AUDIO_ONLY
↓
Worker registers with LiveKit server → waits for room assignment
↓
Job dispatched → entrypoint coroutine called with AgentContext
↓

↓
Agent speaks; user speaks; VAD / turn-taking loop runs until room empty
python — livekit-agents 0.x VoicePipelineAgent
from livekit import agents, rtc
from livekit.agents import AutoSubscribe, JobContext, WorkerOptions, cli
from livekit.agents.voice_assistant import VoicePipelineAgent
from livekit.plugins import deepgram, openai, cartesia, silero

async def entrypoint(ctx: JobContext):
    await ctx.connect(auto_subscribe=AutoSubscribe.AUDIO_ONLY)

    agent = VoicePipelineAgent(
        vad=silero.VAD.load(),
        stt=deepgram.STT(model="nova-3"),
        llm=openai.LLM(model="gpt-4o-mini"),
        tts=cartesia.TTS(voice="a0e99841-438c-4a64-b679-ae501e7d6091"),
        chat_ctx=agents.ChatContext().append(
            role="system",
            text="You are a helpful assistant.",
        ),
    )
    agent.start(ctx.room)
    await agent.say("Hello! How can I help you today?",
                     allow_interruptions=True)

if __name__ == "__main__":
    cli.run_app(WorkerOptions(entrypoint_fnc=entrypoint))
LiveKit SFU — why it matters

A Selective Forwarding Unit receives each participant’s audio track and selectively forwards it to others. For a voice bot, this means the agent never receives the mixed room audio — it receives only the speaking participant’s raw track, so echo-cancellation and cross-talk are handled server-side rather than in your Python process. This is a significant operational advantage over raw WebSocket transport.

OpenAI Realtime API — Speech-to-Speech Architecture

The OpenAI Realtime API (GA November 2024) exposes a persistent WebSocket session that accepts raw audio input and returns audio output, eliminating the separate ASR and TTS hops. The session maintains a server-side conversation context; the client pushes audio frames and receives audio response frames plus text transcripts.

Interruption handling

If the user speaks while the model is responding, the client sends response.cancel followed by input_audio_buffer.clear. The server immediately truncates the in-progress response. The client must also truncate its local playout buffer to the last committed audio chunk reported by response.audio_transcript.delta. Failing to synchronise playout truncation causes the bot to “echo” audio that was cut off server-side.

05

gpt-4o Realtime — Single Model, No STT/TTS Hop

Unlike the classic pipeline where Whisper → GPT-4o → TTS-1 runs sequentially, the gpt-4o Realtime model processes audio input and generates audio output in a single autoregressive pass. The audio tokens are interleaved with text tokens in the same sequence, so the model can “hear” prosody cues (emphasis, hesitation) that are lost when you transcribe first.

Classic pipeline latency breakdown

  • ASR (Deepgram Nova-3): ~180 ms
  • LLM TTFT (gpt-4o): ~320 ms
  • TTS first-chunk (Cartesia Sonic): ~90 ms
  • Total: ~590 ms — under budget, but three round trips

gpt-4o Realtime latency breakdown

  • No ASR hop: 0 ms saved
  • Audio → audio TTFT: ~300–400 ms
  • No TTS hop: 0 ms saved (audio output starts with first token)
  • Total: ~350–400 ms — 40 % faster than classic pipeline

Pricing (as of Q1 2026)

Audio output$200 / 1M tokens (≈ $0.024 / minute of speech)~26× more than text output (gpt-4o: $10 / 1M)

When to choose Realtime API vs. classic pipeline

Choose Realtime API when latency is critical and budget allows, or when you need the model to interpret prosodic cues (e.g. detecting sarcasm, urgency, or emotion from voice). Choose classic pipeline when you need to swap ASR/TTS providers independently (e.g. domain-specific ASR, custom voice clone), when cost-per-minute matters at scale, or when the LLM in your pipeline is not gpt-4o-realtime-preview.

Gemini Live, Claude Voice

Google and Anthropic have both entered the native audio space, each with a different architecture and API surface.

Gemini Live — Google AI Studio / Vertex AI

Architecture

Gemini 2.0 Flash and Gemini 2.5 Pro support native audio input/output via the Google Gen AI Live API (Vertex AI bidiGenerateContent gRPC / WebSocket). Like gpt-4o Realtime, audio tokens are processed in a single model pass. Voices: Aoede, Charon, Fenrir, Kore, Puck (all English, as of Q1 2026). Multilingual audio generation is in preview for Gemini 2.5.

Session config (key fields)

  • model: models/gemini-2.0-flash-live-001
  • response_modalities: ["AUDIO"] or ["TEXT","AUDIO"]
  • speech_config.voice_config.prebuilt_voice_config.voice_name: e.g. "Puck"
  • realtime_input_config.automatic_activity_detection: enable server-side VAD
  • Native tool use via tools array — same format as standard Gemini API

Claude Voice — current state

As of April 2026

Anthropic has not released a native audio-in/audio-out API for Claude. Claude models process text. Voice deployments using Claude use the classic pipeline pattern: ASR (Deepgram / Whisper) → Claude text API → TTS (Cartesia / ElevenLabs). Pipecat and LiveKit both ship first-class Claude adapters for this pattern via AnthropicLLMService / livekit.plugins.anthropic.

Classic pipeline with Claude Haiku

  • Claude 3 Haiku TTFT: ~280 ms median
  • Claude 3.5 Haiku TTFT: ~240 ms median
  • System prompt caching active after first turn (60 % cost reduction on long prompts)
  • Tool use supported via standard API — function-calling frames work natively in Pipecat’s AnthropicLLMContext
Multimodal audio — the trend

All three frontier providers are converging on native audio models that eliminate the ASR/TTS hop. The latency advantage is 30–50 % over a classic pipeline; the quality advantage is prosody-awareness. Expect Claude and Gemini to reach feature parity with the OpenAI Realtime API within 2026, based on current public roadmap signals.

Telephony Bridges (Twilio, SIP)

A large fraction of real-world voice bot deployments run over the PSTN (public switched telephone network) via carriers like Twilio, Vonage, or Bandwidth. These carriers bridge a telephone call to a WebSocket or SIP leg that your agent infrastructure handles. The audio encoding is different: PSTN uses 8 kHz, 8-bit μ-law (G.711 ulaw) rather than the 16 kHz PCM that most ASR models prefer.

Twilio → Pipecat architecture

Key integration points

TwiML <Stream> configuration

Twilio sends 20 ms audio packets (μ-law 8 kHz, 8-bit) as base64-encoded WebSocket messages of type media. The TwilioTransport in Pipecat and the TwilioTranscriptionAgent in LiveKit both decode and resample to 16 kHz PCM before feeding the ASR processor. Configure the TwiML verb: <Stream url="wss://..." track="inbound_track" />.

OpenAI Realtime + Twilio

The OpenAI Realtime API accepts g711_ulaw directly as input_audio_format, removing the resample step. Set output_audio_format to g711_ulaw as well; the Twilio media stream sends it directly back to the PSTN caller. This is the simplest possible Twilio + GPT architecture: phone → Twilio WebSocket → OpenAI Realtime WebSocket → reverse.

SIP trunks vs. Twilio programmable voice

For high-volume enterprise deployments, a raw SIP trunk (RFC 3261) to a Kamailio or Asterisk gateway reduces per-minute carrier cost by 60–80 % compared to Twilio Programmable Voice. LiveKit ships a SIP participant service that bridges PSTN calls via SIP INVITE into a LiveKit room. Twilio is developer-friendly; SIP direct is cost-optimal at >100 K minutes/month.

Picking a Stack

The decision tree below covers the most common real-world scenarios. Starting point: is your transport WebRTC, PSTN, or custom?

Browser / app — WebRTC

LiveKit Agents is the natural fit: LiveKit provides room management, TURN/STUN, SFU, and recording out of the box. Use VoicePipelineAgent with your choice of STT/LLM/TTS plugins. Alternatives: Pipecat with DailyTransport (Daily is built on WebRTC) or SmallWebRTCTransport for a dependency-light path.

Phone (PSTN / Twilio)

Pipecat + TwilioTransport or LiveKit SIP participant. If lowest latency is paramount, wire Twilio WebSocket directly to the OpenAI Realtime API with g711_ulaw on both ends — removes the Python orchestration layer entirely. Use Pipecat when you need custom tool-use logic or a non-OpenAI LLM.

Server-to-server / batch

Classic HTTP pipeline: POST audio → Deepgram transcription REST → LLM chat completion → TTS REST → return audio file. No framework needed. Use Pipecat only if you need conversational state management across multiple turns.

What to Take Away

  • A real-time framework is not optional for production voice. Pipecat and LiveKit Agents both solve the same core problems (transport, VAD, interruption, plugin model) with different transport philosophies. Pipecat is more portable; LiveKit is deeper infrastructure.
  • Pipecat pipeline model: typed frames flow through a chain of asyncio processors. Each processor is independently swappable. The Pipeline([transport.input(), stt, ctx, llm, tts, transport.output()]) pattern is the foundation of most deployments.
  • LiveKit Agents: runs inside a WebRTC room. The SFU hands your agent clean per-participant audio tracks, eliminating echo-cancellation complexity.
  • OpenAI Realtime API removes ASR and TTS hops entirely. First-audio latency ~350–400 ms — 40 % faster than a classic pipeline, at 26–40× the per-token cost of text.
  • gpt-4o Realtime can hear prosody; classic pipeline cannot. For empathetic or emotionally-aware bots, this is the key differentiator.
  • Twilio + PSTN: G.711 ulaw at 8 kHz. Resample to 16 kHz for Whisper/Deepgram, or use OpenAI Realtime with native ulaw passthrough.
